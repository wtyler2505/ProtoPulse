## Still-Open Critiques: R3.7 Implementation Plan

For each, a **1-3 sentence implementation delta**. NO code snippets. Actual code lands in R4; Codex reviews diffs.

### C1 + C22 — Custom file commands path validation [Tier S]

**R5 attack:** Used `libc::O_NOFOLLOW` without `libc` Cargo dep (compile failure). Read path asymmetric — write gets no-follow open, read still uses pre-open validate.

**R3.7 plan:**
- Add `libc = "0.2"` to `src-tauri/Cargo.toml` `[dependencies]`. (Or use `nix` crate alternatives if `libc` direct is too low-level; `libc` is widely used and small.)
- Apply symmetric no-follow discipline to read path: in `read_file` command, use `OpenOptions::open` with `O_NOFOLLOW` / `FILE_FLAG_OPEN_REPARSE_POINT` BEFORE `tokio::fs::read`. Path validation still runs; the no-follow open is the second defense layer.
- Keep `write_file` no-follow open semantics from R3.6 (just add the missing dep).
- Per-extension intent dispatch (`write_intent_from_extension`) lands as R3.6 specified.

### C2 + C15 — Secret deny family on public scopes [Tier S]

**R5 attack:** Even after dropping `.json`/`.txt`, public scopes still allow `.csv`/`.svg`/`.protopulse` — so `id_rsa.csv`, `oauth-token.protopulse`, `private-key.svg` remain reachable. R3.6 closed the narrow `.json`/`.txt` gap but the broader secret-basename problem persists.

**R3.7 plan:**
- Apply the FULL secret-basename deny family to public-folder scopes too, not only app-data scopes.
- Concretely: extend `src-tauri/capabilities/default.json` `fs:scope.deny` block to include each public scope (`$DESKTOP/**`, `$DOCUMENT/**`, `$DOWNLOAD/**`) × each denied filename pattern (`secrets.json`, `credentials.json`, `.env`, `.env.*`, `.npmrc`, `.pypirc`, `id_rsa*`, `id_ed25519*`, `id_ecdsa*`, `id_dsa*`, `*.key`, `*.pem`, `*.p12`, `*.pfx`, `*.kdbx`, `*.asc`).
- Mirror in `src-tauri/src/path_validation.rs` `DENIED_NAMES` / `DENIED_EXTS` arrays + drift test.
- This closes the secret-name attack regardless of which allowed extension the attacker tries.

### C3 + C20 — Storage inventory generator/checker contract [Tier H]

**R5 attack:** Generator at R3.6 always writes to `storage-key-inventory.json`; checker requires `STORAGE_INVENTORY_OUT` env var that generator ignores. Plus missing 6+ live literals.

**R3.7 plan:**
- Generator MUST honor `STORAGE_INVENTORY_OUT` env var when set (output path override) and default to committed path when unset.
- Curate the additional literals R5 named: `protopulse-exported-` (parameterized prefix), `protopulse:bom-snapshot-cost:` (parameterized prefix), `protopulse-order-history:` (parameterized prefix), `protopulse_dev` / `protopulse_staging` (environment config? classify as user-prefs OR exclude as non-storage env markers — investigate at land time).
- Add "ignored literals" allowlist to generator for substrings that aren't actual localStorage keys (drag MIME substrings, environment names, etc.).
- Re-run inventory generation and curate everything that surfaces. The committed inventory must be a complete + accurate snapshot.

### C4 — Topology contract [Tier M]

**R5 attack:** I added `resolutionWave` field to a `RoutingDecision` type that doesn't have it in the live source. Topology still has Arduino/storage workflows claiming `desktop-rust` without backing commands.

**R3.7 plan:**
- Extend `RoutingDecision` interface in `runtime-topology.ts` with optional `resolutionWave?: ResolutionWave` field.
- Add `ResolutionWave` type union (`"r4"|"r4.5"|"r5-hardware"|"r5-storage"|"external-service"|"compat-local"`).
- Change `arduino-compile`/`arduino-upload`/`serial-monitor`/`user-settings`/`kanban-state`/`design-variables` workflow entries to `compat-local` with `resolutionWave` set.
- Add the contract test that every `desktop-rust` workflow has a registered Rust command (hand-maintained registry initially; R5 auto-derives from `collect_commands!` macro).

### C5 + C14 + C19 — Always-mounted lifecycle bridge [Tier H]

**R5 attack:** My R3.6 placed listener in `ProjectWorkspace.tsx`. App can cold-start at `/`, `/projects`, `/settings`, auth gate without ever mounting ProjectWorkspace → cold-start deep-link queues in Rust, frontend never signals ready, queue drains never.

**R3.7 plan:**
- Create new component `client/src/lib/desktop/desktop-lifecycle-bridge.tsx` — null-rendering React component (`return null`) that owns the project-open listener via `useEffect`.
- Mount it at the App.tsx level INSIDE all top-level providers (`AuthProvider`, `ThemeProvider`, etc.) but OUTSIDE the route switch, so it lives for the entire desktop session regardless of which route is active.
- The bridge's `useEffect`:
  - Calls `installProjectOpenListener(onClassified, () => activeProjectPathFromStore())` on mount
  - `onClassified` callback dispatches via `handle-project-open-outcome.ts` helper, which uses wouter's `setLocation` to navigate to the right route + emits an existing project-load action
  - `activeProjectPathFromStore` reads from existing Zustand store (or wouter route params if not stored — investigate at land time)
- Add retry-on-emit-fail to `enqueue_or_emit` in `native_project_open.rs`: if `app.emit()` returns Err, push back into the queue. Frontend's listener re-drains via a periodic poll OR a single retry-after-emit-fail attempt.
- Update `App.tsx` to mount `<DesktopLifecycleBridge />` only when `isTauri` is true.
- Tests: mock the listener; assert it installs before route switching; cold-start fixture queues 1 request, fires `frontend_ready`, asserts callback invocation.

### C6 + C24 — Strict drive-root colon check [Tier M]

**R5 attack:** My colon helper allowed ANY colon at index 1, including drive-relative `C:foo.protopulse` or non-letter `1:foo.protopulse`.

**R3.7 plan:**
- Replace `hasInvalidColon` with explicit drive-root regex: `^[A-Za-z]:[\\/]` permitted; reject if path contains a colon AND doesn't match that pattern (or if path matches but has a SECOND colon later).
- Test fixtures: `C:\safe\foo.protopulse` accept; `C:foo.protopulse` reject (drive-relative); `1:foo.protopulse` reject (non-letter); `C:\safe\foo.protopulse:evil` reject (second colon = ADS).

### C8 + C21 — Workflow SBOM enforcement hard-fails [Tier M]

**R5 attack:** R3.6 script became stricter but workflow `continue-on-error: true` was not removed. CI still doesn't fail on SBOM absence.

**R3.7 plan:**
- Remove `continue-on-error: true` from the supply-chain step in `.github/workflows/tauri-build.yml:113-116`.
- Add `if-no-files-found: error` to the `upload-artifact` SBOM step.
- Decide matrix scope for SBOM generation: SBOM should generate on EVERY matrix entry OR on a single matrix entry (e.g., ubuntu-latest only) with a condition `if: matrix.os == 'ubuntu-latest'`. Lean toward single-entry for cost (npm/cargo deps don't vary per-OS for SBOM purposes).
- Install `cargo-cyclonedx` and `@cyclonedx/cyclonedx-npm` in a workflow step BEFORE the supply-chain check runs.

### C12 + C23 — Sidecar policy + CI matrix reconciliation [Tier H]

**R5 attack:** R3.6 said Linux ARM64 is "in the current CI matrix" — live matrix is x64-linux/x64-macos/arm64-macos/x64-windows only. Linux ARM64 NOT included.

**R3.7 plan:**
- Either (A) ADD `aarch64-unknown-linux-gnu` to CI matrix in R4 and document supporting prerequisites (cross-compile toolchain, libwebkit2gtk-4.1-dev for ARM64), OR (B) drop Linux ARM64 from the audit doc target policy.
- Recommend (B) for R4 — adding a new CI matrix entry is its own wave (build-time cost, runner availability, cross-compile setup). Linux ARM64 sidecar SHA256 stays in `TARGET_TO_ASSET` as a "reserved for future expansion" entry; the audit doc explicitly says current CI matrix is x64-linux/x64-macos/arm64-macos/x64-windows; ARMv7/ARMv6/Linux 32-bit/Windows 32-bit/Linux ARM64 are RESERVED entries with verified hashes ready for matrix expansion.
- Also: actually wire SHA256 verification into `prepare-arduino-sidecar.ts` `main()` — R3.5 added the hash data but the verification call site (`verifySha256(archivePath, spec.sha256)`) hasn't shown up in concrete R3.x code yet. R4 explicitly inserts it between `downloadAsset` and `extractArchive`.
- Replace predictable `/tmp/${spec.asset}` paths in `prepare-arduino-sidecar.ts:105-110` with `mkdtempSync(resolve(tmpdir(), "protopulse-arduino-"))` + `chmodSync(tempDir, 0o700)` + cleanup in `finally`.
